Tour Leader Profiling Modul ALVIS Backoffice & Mobile Apps

Sistem kuesioner profil dinamis untuk meningkatkan kualitas penugasan tur (tour matching & assignment) sesuai kapabilitas Tour Leader Panorama JTB. Mengintegrasikan kemudahan pengelolaan pertanyaan oleh Admin di Backoffice dengan alur pengisian intuitif di Mobile Apps.

27 Agustus 2026 Backoffice + Mobile Status: Approved for Dev Dokumen ID: BRD-ALVIS-TLP-2026-V1

Ringkasan Eksekutif

Ringkasan 1 halaman untuk manajemen & stakeholder. Berisi intisari masalah, solusi, dan dampak bisnis yang diharapkan dari proyek ini.

Solusi Digitalisasi

Sistem profiling terpusat: Admin mengelola pertanyaan via Backoffice (CRUD tanpa deploy app), TL mengisi via Mobile Apps dengan auto-save dan progress tracking.

Hasil yang Diharapkan

Pengumpulan data lebih mudah dan lebih efisien. Data TL tersimpan terstruktur di ALVIS. Admin leluasa mengubah pertanyaan, TL nyaman mengisi lewat HP.

Tujuan Inti

Mendigitalisasi proses pengumpulan data profil TL yang selama ini manual, agar lebih mudah, terstruktur, dan efisien — baik dari sisi Admin (pengelola pertanyaan) maupun TL (pengisian jawaban).

1. Pendahuluan

1.1 Latar Belakang

Tour Leader (TL) merupakan garda terdepan dalam operasional tur Panorama JTB. Saat ini, pengumpulan data kualitatif TL — seperti keahlian khusus, penguasaan bahasa asing, riwayat lisensi/sertifikasi, hingga catatan diet atau kondisi kesehatan khusus — masih dilakukan secara manual menggunakan spreadsheet atau formulir terpisah, dan belum terintegrasi dengan ALVIS.

Untuk mendigitalisasi proses pengumpulan data tersebut agar lebih mudah, terstruktur, dan efisien, diperlukan sebuah sistem kuesioner profil dinamis (Tour Leader Profiling). Sistem ini memungkinkan Admin mengelola pertanyaan secara mandiri di Backoffice dan TL mengisi profil dengan nyaman melalui ALVIS Mobile Apps.

1.2 Tujuan Proyek

  • Dinamisasi Pengaturan: Memungkinkan Admin/Operations mengelola pertanyaan profiling (CRUD) tanpa perlu merilis pembaruan (deployment) aplikasi mobile secara berkala.
  • Alur Pengisian Tanpa Hambatan: Menyediakan alur pengisian berkonsep Auto-Save on Transition di Mobile Apps agar TL dapat melengkapi kuesioner secara intuitif tanpa khawatir kehilangan data.
  • Transparansi Data Operator: Menyediakan visualisasi jawaban profiling secara komprehensif pada Halaman Detail Tour Leader di ALVIS Backoffice.
  • Potensi Pengembangan Lanjutan: Struktur data profil yang dibangun dapat menjadi dasar untuk fitur tambahan di masa depan (misalnya: filter atau laporan kapabilitas TL).
    Catatan: pengembangan fitur lanjutan berada di luar lingkup dokumen ini.

1.3 Asumsi & Ketergantungan

A. Asumsi

  • Seluruh TL aktif memiliki akses ke ALVIS Mobile Apps versi terbaru yang kompatibel dengan fitur auto-save.
  • Koneksi internet TL dianggap tersedia pada umumnya; skenario offline ditangani secara terbatas (lihat Section 9).
  • Admin/Operations memiliki pemahaman dasar mengenai kategori pertanyaan yang relevan untuk kebutuhan operasional.
  • Perangkat TL memenuhi kapasitas minimum (RAM & storage) untuk menjalankan fitur profiling tanpa degradasi performa aplikasi.

B. Ketergantungan (Dependencies)

  • Internal: Ketersediaan API Service Layer ALVIS, Schema Master Data tour_leaders, dan modul notifikasi Mobile Apps.
  • Tim: Koordinasi dengan Tim Mobile (auto-save & offline cache), Tim Backoffice (CRUD + export), dan Tim Database (schema audit log).
  • Compliance: Data kesehatan dan diet termasuk data sensitif (PII) — pengelolaan wajib memperhatikan UU PDP dan kebijakan privasi internal Panorama.
  • Infrastruktur: Local storage pada Mobile (SQLite/MMKV) tersedia untuk cache offline; capacity & retention policy mengikuti standar mobile app ALVIS.

Catatan Desain UX (Auto-Save on Transition)

TL tidak perlu menekan tombol "Simpan" secara manual. Setiap perpindahan ke pertanyaan berikutnya, sistem mengirim payload jawaban secara asynchronous di background. Jika terjadi kegagalan koneksi, jawaban disimpan di local storage dan di-retry otomatis saat online.

5. Logika Perhitungan Kelengkapan Profil

Persentase kelengkapan profil dihitung secara dinamis hanya berdasarkan pertanyaan yang ditandai sebagai Required (Wajib) dan berstatus Active.

Formula % Completeness

% Completeness = (Total Pertanyaan Wajib Aktif Dijawab TL / Total Pertanyaan Wajib Aktif) × 100%

5.1 Aturan Edge Case untuk Kalkulasi

  • Pertanyaan yang di-soft-delete (kolom deleted_at terisi) tidak dihitung dalam divisor dan numerator.
  • Jika pertanyaan required diubah menjadi optional, jawaban existing tetap dihitung; kalkulasi ke depan melewati pertanyaan tersebut.
  • Jawaban kosong (null) dianggap belum dijawab, termasuk untuk pertanyaan multiple choice tanpa pilihan yang dicentang.
  • Pembulatan dilakukan ke bilangan bulat (floor) untuk konsistensi tampilan badge.

6. Skema Basis Data (High-Level)

Diperlukan 3 tabel baru pada basis data MySQL ALVIS, mengikuti pola schema existing tour_tmst_* (master table dengan kolom sys_* audit standard). Ketiga tabel terhubung dengan tabel tour_tmst_tour_leader yang sudah ada (FK ke tl_id). Riwayat perubahan cukup ditangani oleh kolom sys_update_user, sys_update_date, dan sys_soft_delete; data jawaban TL sementara disimpan di local device (SQLite/MMKV) sebelum dikirim ke server.

Catatan Adopsi Pola Schema

Schema ini mengadopsi pola dari fitur serupa (tour_tmst_survey_*) yang sudah berjalan di ALVIS: 3-tabel (group + question + answer), kolom sys_* untuk audit, soft delete yang trackable, dan dukungan _guid untuk sinkronisasi dari local storage. Penamaan mengikuti prefix tour_tmst_tlpr_* agar jelas scope-nya (Tour Leader Profiling).

7. API Specification for Bridge Integration

API untuk menyediakan data tour leader profiling dan tour leader scoring ke sistem lain melalui mekanisme bridge integration. Satu service endpoint dapat mengambil data untuk 1 tour leader atau beberapa tour leader sekaligus dalam satu request.

Spesifikasi Singkat

Base URL: https://apps-alvis.icore.studio/tour-service/api/v2

Method: GET — query parameter tl_ids (1 atau banyak, comma-separated).

Endpoint: /tour-leaders/profiling

Authentication: Header X-API-Key: {bridge_api_key}.

Rate Limit: 100 request/menit per API Key.

Request & Response

# Request (1 TL) GET /tour-leaders/profiling?tl_ids=123 Headers: X-API-Key: your_bridge_api_key # Request (multiple TL) GET /tour-leaders/profiling?tl_ids=123,456,789 Headers: X-API-Key: your_bridge_api_key # Response [ { "tl_id": 123, "tl_name": "Aang Maratona", "profiling": { "completeness": 60, "answers": [ { "question_id": 1, "question_text": "...", "answer_value": "Ya" } ] }, "scoring": { "avg_score": 9.63, "total_tours": 3, "tier": "Senior" } }, { "tl_id": 456, "tl_name": "...", "profiling": { ... }, "scoring": { ... } } ]
Fitur Utama
  • Satu endpoint untuk semua kebutuhan integrasi (simplifikasi maintenance).
  • Support single atau batch retrieval dalam satu call.
  • Response berisi profiling (jawaban kuesioner) dan scoring (rata-rata skor, total tours, tier) sekaligus.
  • API Key di-generate per-bridge dari Backoffice (dapat di-revoke).

8. Kriteria Penerimaan (Acceptance Criteria)

Daftar 10 kriteria yang harus dipenuhi agar fitur dianggap lulus QA.

  • AC-01 Admin sukses menambah, merubah, menonaktifkan, dan melakukan soft-delete pertanyaan profiling di Backoffice.
  • AC-02 Pertanyaan baru yang diset sebagai Required secara otomatis memutakhirkan kalkulasi % kelengkapan seluruh TL secara real-time.
  • AC-03 Banner profiling tampil di Landing TL (Tab TL) dan halaman Profile, baik saat progres <100% maupun sudah 100%. Banner tidak auto-hide.
  • AC-04 Pengisian jawaban di Mobile App berhasil tersimpan otomatis tanpa error ketika TL berpindah halaman pertanyaan (Auto-Save on Transition), termasuk pada skenario offline → online.
  • AC-07 Setiap perubahan oleh Admin (edit pertanyaan, edit jawaban, soft-delete) secara otomatis memperbarui kolom updated_at dan updated_by pada record terkait.
  • AC-09 Skema versioning: perubahan teks pertanyaan tidak memengaruhi jawaban historis; jawaban lama tetap merujuk pada versi pertanyaan saat dijawab.
  • AC-10 Validasi input berjalan di client & server: Short Text maks 200 karakter, Long Text maks 2000 karakter, Rating Scale hanya 1-5.
  • AC-11 API Bridge dapat mengambil data profiling & scoring TL via GET /tour-leaders/profiling?tl_ids=... dengan API Key valid; support 1 atau banyak TL (comma-separated) dalam satu request.
  • AC-12 API endpoint terautentikasi via header X-API-Key; rate limiting 100 request/menit per key.
  • AC-13 Admin/Operations dapat generate dan revoke API Key per bridge dari halaman Backoffice. Log akses API tercatat untuk audit (timestamp, endpoint, response code).

9. Edge Cases & State Transitions

9.1 Skenario Concurrency
Skenario Perlakuan Sistem Pesan ke User
Admin ubah pertanyaan yang sedang dijawab TL. Jawaban TL disimpan dengan question_version lama; Admin membuat versi baru. "Pertanyaan telah diperbarui oleh Admin. Jawaban Anda sebelumnya tetap tersimpan."
Admin edit jawaban TL langsung di Backoffice. Last-write-wins dengan logging; jawaban Admin ditandai updated_by = admin username. "Jawaban Anda untuk pertanyaan X telah diperbarui oleh Admin."
TL jawab dengan koneksi terputus > 5 menit. Data disimpan ke SQLite/MMKV. Retry exponential backoff (1m, 5m, 15m) saat online. Indikator "Menunggu koneksi..." pada header wizard.
Admin soft-delete pertanyaan aktif + sudah dijawab. Pertanyaan hilang dari daftar aktif; jawaban existing di-archive, tidak dihitung di % completeness. Admin: "Pertanyaan di-nonaktifkan; 12 jawaban historis diarsipkan."
Branching: TL ganti jawaban parent yang trigger child questions. Sistem menghapus jawaban child questions yang bergantung pada nilai parent (cascade delete pada level aplikasi). Jawaban parent yang baru akan trigger child questions sesuai aturan. TL melihat child questions baru atau anak-anak hilang sesuai logika branching.
Sync offline: TL isi 5 pertanyaan offline, lalu online dengan Admin update pertanyaan. Sistem mencocokkan via _guid. Jawaban offline yang referensinya sudah dihapus Admin di-drop; jawaban valid tetap dikirim dengan version terbaru dari server. Indikator "Sinkronisasi..." lalu "Semua jawaban tersimpan" / sebagian "3 dari 5 jawaban tersimpan, 2 dilewati (perubahan di server)".
9.2 Validasi & Error Handling
  • Input teks > batas karakter → inline error: "Maksimal 200/2000 karakter".
  • Rating Scale di luar 1-5 → error: "Nilai harus 1-5".
  • Auto-save gagal 3x berturut-turut → modal: "Gagal menyimpan. Jawaban tersimpan di perangkat dan akan dikirim otomatis saat koneksi stabil."
  • Akun dinonaktifkan saat wizard → redirect ke halaman error 403 dengan instruksi hubungi HR.

% CompletenessPersentase kelengkapan profil TL; dihitung dari jumlah pertanyaan wajib aktif yang sudah dijawab dibagi total pertanyaan wajib aktif.
Auto-Save on TransitionMekanisme penyimpanan otomatis jawaban tanpa tombol "Simpan"; terjadi saat user memilih opsi, mengetik (debounce 1s/blur), atau berpindah pertanyaan.
Soft DeletePenghapusan logis dengan mengisi kolom sys_soft_delete = 1; data tetap ada di database untuk audit tapi tidak muncul di UI aktif. Disertai sys_delete_user dan sys_delete_date.
WizardAntarmuka pengisian pertanyaan satu per satu dengan navigasi Next/Back di Mobile.
Question VersionNomor versi sebuah pertanyaan (kolom sq_version); bertambah setiap kali teks pertanyaan diubah. Jawaban historis merujuk ke versi saat dijawab (snapshot di sa_question_version).
DebounceTeknik menunda eksekusi fungsi sampai aktivitas berhenti selama durasi tertentu (1000ms).
MMKVLibrary key-value storage ringan untuk mobile (Android/iOS); alternatif SQLite untuk cache lokal.
PIIPersonally Identifiable Information — data yang dapat mengidentifikasi individu; diperlakukan sesuai UU PDP.
RBACRole-Based Access Control — kontrol akses berbasis peran user.
BRDBusiness Requirement Document — dokumen formal yang menjabarkan kebutuhan bisnis suatu fitur.
ACAcceptance Criteria — kriteria yang harus dipenuhi agar fitur dianggap lulus QA.
Question GroupKelompok/kategori pertanyaan (misal: Keahlian, Bahasa, Lisensi). Disimpan di tabel tour_tmst_tlpr_question_group.
Branching LogicLogika pertanyaan kondisional — pertanyaan child hanya muncul jika jawaban parent memiliki nilai tertentu. Diatur via sq_parent_id + sq_parent_value.
GUIDGlobally Unique Identifier (varchar 50). Digunakan untuk sinkronisasi data antara local device (Mobile) dan server. Format UUID atau custom.
Snapshot VersionPenyimpanan versi pertanyaan saat jawaban disimpan (sa_question_version). Memastikan jawaban historis tetap merujuk ke versi pertanyaan yang dijawab, walau Admin sudah update pertanyaan.
Bridge APIAPI read-only di ALVIS yang digunakan sistem lain untuk mengambil data profiling & scoring TL tanpa integrasi langsung ke database. Endpoint: GET /tour-leaders/profiling?tl_ids=...
Tour Leader ScoringSkor rata-rata (avg_score) dari feedback tur yang dikumpulkan TL; berbeda dari data profiling yang isinya jawaban kuesioner. Dikembalikan bersamaan oleh Bridge API di field scoring.

11. Spesifikasi Design Mobile (UX Specification)

Spesifikasi design final untuk komponen UI di ALVIS Mobile Apps berdasarkan hasil eksplorasi desain (lihat mockup-tl-profiling-banner.html).

Design Decision

Berdasarkan analisis 3 konsep alternatif, disepakati menggunakan Konsep 2 (Full Progress Card) untuk Landing Tour Leader dan Konsep 1 (Settings List Item) untuk Profile Page. Keduanya menggunakan circular progress indicator sebagai visual language yang konsisten.

TMP11.1 Prinsip Desain
  • Konsistensi Visual: Circular progress (orange conic-gradient) di kedua layar dengan ukuran berbeda (56px di Landing, 32px di Profile).
  • Primary Color Harmony: Orange #ea580c konsisten dengan design system ALVIS.
  • State-Driven: Progress dinamis mengikuti data real-time; transisi halus 300ms.
  • Hierarchy Jelas: Landing = high prominence (primary entry); Profile = low prominence (secondary).

TMP11.6 Aksesibilitas (Accessibility)
  • Seluruh card / item tap-area memenuhi standar minimum 44x44 px (Apple HIG) / 48x48 dp (Material).

  • Mendukung reduced motion: animasi progress arc di-disable dan langsung snap ke nilai akhir.
